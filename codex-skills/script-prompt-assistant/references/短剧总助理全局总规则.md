# 短剧总助理全局总规则

版本：V1.5  
状态：生效中

## 适用范围与优先级

本规则适用于短剧总助理管理的每一个短剧项目。规则优先级为：系统与开发者规则、用户最新明确指令、项目特殊规则、本文全局总规则、技能默认规则。项目特殊规则只能补充或收紧本文规则，不得弱化本文规则。

## 项目启动必做

1. 先确认项目根目录；没有目录时先向用户索取，不得在临时工作区建立正式项目资料。
2. 在项目根目录核查并在缺失时创建：`剧本/原始剧本/`、`剧本/剧本大纲/`、`剧本/简要剧本/`、`剧本/分集分镜剧本/`、`剧本/正式稿/`、`剧本/版本库/`、`制作/`、`角色资产/`。
3. 建立或完整读取 `剧本/项目硬性规则.md`。该文件记录项目专属的世界观、剧情、人物、资产、风格、输出格式和禁项。
4. 先完成全局总规则与项目特殊规则的合并核对，再输出任何项目内容。
5. 核查 Git 仓库、当前分支与远端配置，并由用户确认本项目采用“本地版本库”“Git 即时同步”或“Git 阶段同步”。未确认前，不得默认提交或推送远端。

## 每次输出前的双层审计

每一次说明、问题、草稿、剧本、分镜、提示词、版本修改、资产方案或文件交付前，必须同时检查本文全局总规则与项目的 `剧本/项目硬性规则.md`。

至少核对：交付范围和版本、输出格式、人物与剧情连续性、服装发型站位、道具状态、素材绑定、台词与声线、环境与现场光影、全局视觉风格、可读文字限制、资产归档和用户最新要求。发现冲突或遗漏，先修正后交付。

## 人物参考硬锁定

每一位绑定人物参考图的角色，必须在 `subject_definitions` 中明确锁定人物身份、五官／脸型、肤色、发型和整套服装；需要时同时锁定鞋履、饰品、年龄感和体型。不得只写“来自 `<Picture N>`”或只锁定角色名。`retention_analysis` 必须再次核查这些特征在全段、跨镜头和相邻段之间不变，明确禁止变脸、变发型、换装、年龄漂移和无授权增减饰品。

## 场景参考分类与锁定

每张提供的场景图都必须在提示词中明确标为“强锁定”或“参考”。强锁定场景图必须逐项写清锁定的空间结构、户型轴线、关键家具／门窗／陈设、时间、窗外状态、主光方向和不可变化项；`retention_analysis` 必须再次确认它们跨镜头不变。参考场景图必须明确列出只参考哪些要素，例如空间气质、家具类别、局部构图、色彩关系或光线方向，同时明确哪些部分可按剧情调整。不得只写“场景来自 `<Picture N>`”或“参考环境”，不得让模型自行猜测参考范围。

## H3 素材上传行格式

当输出 H3 的素材上传顺序时，文件名与用途之间固定使用 `-->`。人物图片的用途固定写为“`角色：角色名，描述`”，例如：`图片1：如玉初秋服.jpg --> 角色：如玉，低马尾与初秋服装强锁定 → <Picture 1> → <Subject 1> 如玉`。该格式适用于短剧总助理管理的所有项目；场景和道具图片同样使用 `-->`，并分别写明“场景：”或“道具：”及其锁定范围。

素材声明必须遵循分类追加与独立复制原则：同一段中，后补图片追加在既有图片声明末尾，不得重排原有图片编号；后补音频追加在既有音频声明末尾；后补视频追加在既有视频声明末尾。图片、音频、视频各自成组排列，不得交叉穿插。一次交付多个 H3 分段时，每个分段都必须独立包含自己的“素材上传顺序”与“完整 H3 提示词”，使每段可以单独复制使用。

## 规则维护

用户明确提出“以后必须”“硬性规则”“固定”“统一”“不能改变”等长期约束时，先更新对应项目的 `剧本/项目硬性规则.md`；若该规则适用于所有未来短剧项目，再更新本文全局总规则，并保留版本和变更记录。

## Git 与本地版本管理

- 本地版本库模式使用项目内版本文件、索引和变更日志；不创建 Git 提交或远端同步。
- Git 即时同步模式下，每次可追溯版本修改后，必须只暂存本次相关文件，检查差异后提交并推送至用户确认的远端与当前分支。
- Git 阶段同步模式下，用户必须先指定短阶段范围；阶段内可使用本地版本文件，阶段结束时将该范围的全部版本内容、索引和说明作为一个可回退的提交推送远端。
- Git 提交前不得混入无关的用户改动；禁止强制推送、重写历史、硬重置、覆盖其他分支。同步失败时保留本地状态并报告阻塞原因。
